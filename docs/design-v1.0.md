## 0장. 문서 개요

### 0.1 목적

이 문서는 2026년 대전 소상공인·자영업자 재기지원사업(대전일자리경제진흥원 발주, 넥스트랩 운영)의 운영관리 플랫폼을 구축하기 위한 설계 명세다. 진흥원(발주기관)·넥스트랩(운영대행사)·멘토·멘티 4개 역할이 하나의 케이스(지원 대상 건)를 12단계 워크플로우로 순차 처리하는 내부 업무관리 시스템을 대상으로 한다.

### 0.2 문서 성격

이 프로젝트는 일반 SaaS·이커머스형 플랫폼이 아니라 "내부 도구(워크플로우·승인 관리 시스템)" 유형이다. 따라서 표준 8단계 설계 방법론 중 결제(PG)·SEO·다국어·회원 셀프가입 관련 항목은 이 사업 구조에 맞게 단순화하거나 제외했고, 대신 역할별 권한, 승인 워크플로우, 상태값 설계, 감사로그에 비중을 크게 두었다.

### 0.3 문서 구성

1~2장은 사업 정체성과 핵심 워크플로우, 3장은 역할·권한, 4장은 문서·서명 처리, 5장은 화면 구조, 6장은 알림 체계, 7장은 백오피스, 8장은 비기능 요건, 9~11장은 기술 스택·데이터 모델·로드맵, 12장은 외부 연동, 13장은 클로드 코드 인계 가이드, 14장은 법적·개인정보 문서 초안이다.

### 2.0 케이스 등록 입력 항목 (접수신청서 기준)

1단계에서 진흥원이 입력하는 항목은 실제 사업신청서(붙임1) 양식의 필드를 그대로 따른다: 업체명(상호명), 대표자명, 사업자등록번호, 대표 휴대번호(연락처), 사업장 주소, 이메일, 업태, 종목, 개업연월일, 상시근로자수. 폐업정리 유형은 추가로 폐업/폐업예정 구분, 폐업(예정)연월일, 2025년 매출액, 임대차보증금, 월세금액을 입력한다. 이 항목들은 이후 지원신청서·완료보고서 등 문서 자동생성 시 재사용된다.

### 2.2 상태 전이 규칙

각 단계는 "이전 단계 완료" 조건이 충족되어야 다음 단계로 이동 가능 (역방향 순서 위반 차단)

각 단계 전이는 담당 역할만 실행 가능 — 서버(Route Handler/RLS)에서 재검증, 클라이언트 숨김만으로 차단 금지

8단계(진흥원 반려) 시 케이스는 별도 "반려" 상태로 분기, 재보완 후 7단계로 재진입 가능

모든 상태 변경은 case_status_history에 자동 기록 (누가/언제/이전상태/이후상태)

## 3장. 회원·권한 모델

### 3.1 계정 생성 방식

전원 관리자(진흥원·넥스트랩)가 계정을 직접 발급한다. 셀프 회원가입 플로우가 없으므로 이메일 인증·소셜로그인·연령확인(정통망법 14세 조항) 등 일반 B2C 가입 로직이 불필요해 개발 범위가 단순해진다. 단, 멘티는 예외적으로 자신의 케이스가 등록된 후 넥스트랩이 초대 링크(임시 비밀번호 또는 매직링크)를 발급해 최초 로그인 시 본인 확인 후 계정을 활성화하는 방식을 권장한다.

⚠ 짚을 포인트 — 승인 권한 단일화의 함정
진흥원 담당자 1명만 승인 권한을 갖는 구조는 명확하지만, 담당자 휴가·부재 시 병목이 생긴다. 백오피스에 "승인 대기일수" 알림과, 관리자가 임시로 대리 승인권을 부여할 수 있는 "권한 위임" 기능을 로드맵(11장)에 포함해두는 것을 권장한다.

### 3.3 로그인 방식

이메일 + 비밀번호 기반 로그인을 기본으로 하고, 최초 로그인 시 비밀번호 재설정을 강제한다. 소셜로그인(카카오·구글)은 불필요 — 관리자 발급 계정 구조와 맞지 않는다.

### 3.4 수집 정보 (멘티 개인정보 포함)

멘티는 소상공인 개인정보(사업자정보, 연락처, 계좌정보 등)를 포함해 정보를 제공하므로 개인정보보호법상 수집·이용 동의가 필요하다. 세부 항목은 14장 참조.

## 4장. 문서·서명 처리 (결제 모델 대체)

이 플랫폼은 사용자로부터 결제를 받지 않는 위탁운영 관리도구이므로 PG(결제대행) 연동이 없다. 대신 "서류·서명 업로드"가 결제 단계에 준하는 핵심 트랜잭션이다.

### 4.1 서명 처리 방식

멘토·멘티 서명은 태블릿/터치 서명 캡처(캔버스 서명)로 처리한다. react-signature-canvas 등으로 서명을 이미지(PNG, base64)로 저장하고, Supabase Storage에 업로드 후 URL을 signatures 테이블에 기록한다. 서명 시점의 서명자, 케이스ID, 문서종류, IP를 함께 저장해 법적 증빙력을 높인다.

### 4.2 서류 업로드 구조

공사·설비업체는 시스템 계정이 없으므로, 멘티 또는 멘토가 대신 업로드한다.

업로드 문서는 documents 테이블에 케이스ID·단계·문서유형·업로더 역할과 함께 저장

문서유형은 지원유형(경영개선/폐업지원)별 필수서류 매핑 테이블(support_type_documents)로 관리, 필수서류 미제출 시 다음 단계 진행 차단

### 4.3 대금 지급 처리

업체에 대한 대금 지급은 플랫폼 밖(계좌이체)에서 이뤄지며, 플랫폼은 이체확인서·하자보수서약서 등 증빙서류의 업로드·검증·보관 역할만 수행한다. 즉 이 시스템에 결제 도메인은 없고 "증빙관리" 도메인만 존재한다.

### 4.4 붙임서식 자동생성 파이프라인 (hwp 원본 서식 재현)

진흥원 실제 붙임서식(hwp)은 레거시 바이너리 포맷이라 프로그램적으로 직접 값을 채워 넣을 수 없다. 대신 다음 파이프라인으로 원본과 동일한 레이아웃의 최종 문서를 자동 생성한다.

1) 사전 작업(1회): hwp5(pyhwp)로 각 붙임서식을 HTML로 변환한다. 이 결과물은 원본의 표 구조·셀 폭(mm)·글자모양·문단 서식을 그대로 보존한 HTML/CSS이다.

2) 이 HTML을 코드 템플릿화한다: 빈 입력칸(상호명, 사업자등록번호, 지원금액 등)을 {{필드명}} 형태의 플레이스홀더로 치환하고, 체크박스(위생관리/안전관리 등)는 조건부 마크(☑/☐) 렌더링으로 바꾼다.

3) 런타임: "지원신청서 작성", "완료보고서·지급신청서 작성" 단계에서 케이스 데이터(cases, support_applications, documents 등)를 템플릿에 주입한다.

4) 헤드리스 브라우저(Puppeteer/Playwright)로 최종 HTML을 PDF로 렌더링한다. 이 PDF가 진흥원에 제출되는 실제 산출물이며, 원본 hwp 서식과 표 구조·글자 배치가 동일하다.

⚠ 짚을 포인트 — 웹 화면 자체를 서식처럼 만들 필요는 없다
멘토·넥스트랩이 데이터를 입력하는 웹 화면은 일반적인 폼(입력창, 체크박스, 드롭다운)이면 충분하다. 원본 서식의 표 구조를 웹 화면에 그대로 재현할 필요는 없고, "제출용 최종 문서를 생성하는 시점"에만 원본과 동일한 레이아웃을 적용하면 된다. 이 원칙 덕분에 화면 개발은 표준적인 shadcn/ui 폼으로 단순하게 가져갈 수 있다.

⚠ 짚을 포인트 — 서식이 개정되면 템플릿만 교체
진흥원이 매년 공고 시 붙임서식을 미세 조정하는 경우가 흔하다. 서식별 HTML 템플릿을 코드가 아닌 데이터(document_templates 테이블 또는 별도 템플릿 파일 저장소)로 관리하면, 서식 변경 시 개발자 재작업 없이 템플릿 파일만 교체하면 된다.

⚠ 짚을 포인트 — 서명·서류의 법적 증빙력
정산서류는 3년 보관이 필요하며 감사 대상이 될 수 있다. 서명 이미지·업로드 파일의 원본 무결성(변조 방지)을 위해 파일 해시값(SHA-256)을 documents 테이블에 함께 저장해두면, 추후 감사 시 원본성 입증에 도움이 된다.

## 6장. 알림·소통 체계

### 6.1 자동 통보 방식

승인 시 넥스트랩/멘토/멘티에게 보내는 자동 통보는 카카오 알림톡을 기본으로 하고, 알림톡 발송 실패(미가입·차단 등) 시 SMS로 자동 대체(fallback)하는 방식을 사용한다.

⚠ 추천 근거
알림톡은 SMS 대비 발송비용이 낮고(건당 약 9~15원 vs SMS 20원대) 템플릿 기반이라 승인/반려 등 정형화된 공식 통보에 적합하다. 단, 카카오톡 미가입자·차단자에게는 도달하지 않으므로 SMS 대체 발송으로 도달률을 보장해야 한다. 연 30~100건 규모에서는 월 발송비용이 수만원 수준으로 크지 않다.

⚠ 짚을 포인트 — 백오피스 모바일 대응
멘토는 현장 방문 중 모바일로 멘토링 일지·서명을 등록해야 하므로 멘토용 화면은 모바일 필수다. 반면 진흥원·넥스트랩의 전체 현황·통계 조회는 PC 위주 작업이 많지만, 승인처리처럼 간단한 액션은 모바일에서도 가능해야 한다 (8.1절 참조).

## 8장. 비기능 요건

### 8.1 모바일 대응

반응형 동등 수준으로 개발한다. 특히 멘토(현장 방문·서명 캡처)와 멘티(서류 업로드)는 모바일 사용 비중이 높으므로 해당 화면은 모바일 우선으로 설계하고, 진흥원·넥스트랩의 조회·승인 화면도 모바일에서 100% 정상 동작해야 한다.

### 8.2 다국어

한국어 단일 언어. i18n 사전 대비 불필요 (내부 도구, 국내 사업 전용).

### 8.3 법적 요건 수준

일반 소비자 대상 서비스가 아니므로 전자상거래법·정통망법 마케팅동의 조항은 해당사항이 적으나, 멘티의 개인정보(사업자정보·계좌정보 등 민감성 있는 정보)를 수집·처리하므로 개인정보보호법 기준의 개인정보처리방침과 수집·이용 동의는 반드시 필요하다. 세부는 14장 참조.

### 8.4 호스팅 환경

Vercel(프론트) + Supabase(DB·인증) 조합을 사용한다. 진흥원 계약상 국내 클라우드 제한 요구사항이 없어 해외 SaaS 사용이 가능하나, Supabase는 반드시 서울 리전(ap-northeast-2)을 사용해 개인정보 국외이전 이슈를 원천 차단한다.

### 8.5 데이터 보관 기간

정산서류·대상문서는 3년 보관을 기본으로 한다 (일반 공공사업 정산서류 관례). 감사로그는 별도로 사업 종료 후에도 장기 보관을 권장한다.

### 8.6 디자인 톤

클로드가 직접 디자인 시안을 제작한다. 공공위탁 운영도구 특성상 화려한 마케팅 톤이 아닌, 신뢰감 있고 명확한 정보 전달 중심의 관리형 UI(진흥원·정부 협업툴에 어울리는 차분한 블루/그레이 톤)를 기본 방향으로 한다. 상세 토큰은 클로드 코드 6단계(디자인 토큰 정의)에서 확정한다.

### 8.7 성능·보안

일반 수준(LCP < 2.5초)이면 충분하다. 개인정보·서명·서류가 오가므로 Supabase RLS 전면 적용, 업로드 파일 접근은 서명된 URL(signed URL) 방식으로 제한한다.

## 13장. 클로드 코드 인계 가이드

### 13.1 5줄 요약

대전 재기지원사업의 진흥원·넥스트랩·멘토·멘티 4개 역할이 12단계 케이스 워크플로우를 처리하는 내부 관리 플랫폼이다. 계정은 전원 관리자 발급, 결제·다국어·SEO는 없다. 핵심은 상태 전이 규칙의 서버사이드 강제, 지원유형별 필수서류 매핑, 캔버스 서명, 알림톡+SMS 통보, 감사로그다. 기술스택은 Next.js+Supabase(서울)+Vercel.

### 13.2 작업 단계 개요

아래 프롬프트 시퀀스 문서(총 15단계)를 클로드 코드에 순서대로 투입한다. 각 단계 완료 후 체크리스트를 확인하고 commit 한다.

### 13.3 절대 잊지 말아야 할 핵심 결정사항

결제(PG) 없음 — 대금지급은 플랫폼 밖에서 발생, 증빙서류만 관리

계정은 관리자 발급만 — 셀프 회원가입 로직 불필요

상태 전이는 반드시 서버(Route Handler/RLS)에서 재검증

지원유형별 필수서류·한도는 하드코딩 금지, 관리자 화면에서 관리

Supabase는 서울 리전 고정

감사로그는 INSERT only

### 13.4 CLAUDE.md

별도 CLAUDE.md 파일로 함께 제공한다. 프로젝트 루트에 그대로 저장해 매 클로드 코드 세션에서 참조한다.

## 14장. 개인정보·법적 문서 개요

이 시스템은 일반 소비자 대상 셀프가입 서비스가 아니지만, 멘티(소상공인)의 개인정보를 수집·처리하므로 개인정보보호법 기준의 문서가 필요하다. 상세 초안은 별도 "법적 약관 초안" 문서로 제공한다.

개인정보 수집·이용 동의서 (멘티용)

개인정보처리방침 (내부 운영용, 진흥원·넥스트랩 공동)

시스템 이용수칙 (관리자 발급 계정 대상, 일반 이용약관 대체)

⚠ 변호사 검토 필수
본 장 및 별도 법적 약관 문서는 일반적 구조의 초안(template)이다. 실제 운영 전 반드시 법무 전문가 검토를 받아야 하며, 진흥원과의 위탁계약서상 개인정보 처리 조항과 반드시 정합성을 확인해야 한다.
