# 모두의창업 플랫폼 — 침해사고 대응 절차 (Incident Response)

> 작성일 2026-09-28 (P35, 사용자 결정 ⑩ 반영) · 상위 문서 `docs/SECURITY-POLICY.md`(§5-6 요약표 · §8 해킹 시도 인지·대응 정책) · 복구 절차 `docs/BACKUP-RESTORE.md` · 배포 되돌리기 `docs/DEPLOY-RUNBOOK.md §7`
> 이 문서는 **"개인정보나 업무정보가 권한 없는 사람에게 갔을 수 있다"고 판단된 순간부터** 적용한다. 그 전 단계(신호 감지·계정 잠금·IP 차단)는 `SECURITY-POLICY.md §8-3` 을 따른다.
> 기관명은 쓰지 않는다 — `{발주처}` `{운영사}` 는 행사 기본 설정(`programs.client_name / operator_name`)에 등록된 이름을 뜻한다.

---

## 0. 한눈에 보는 순서와 시한

```
신고 접수(즉시) → 초동 조치(15분~1시간) → 영향 범위 산정(24시간) → 통지(인지 후 72시간) → 재발 방지(2주) → 기록(사고 종결 시)
```

| 단계 | 시한(사고 인지 시각 기준) | 주 담당 | 산출물 |
|---|---|---|---|
| 1 신고 접수 | 즉시 | 발견자 → {운영사} PL | 사고 번호·인지 시각·최초 상황 메모(§6 양식 A) |
| 2 초동 조치 | critical 15분 · 그 외 1시간 | {운영사} PL + 플랫폼 관리자 | 잠금·차단·되돌리기·키 로테이션 체크(§2) |
| 3 영향 범위 산정 | 24시간 | {운영사} PL(+플랫폼 관리자) | 대상자 수·항목·기간·경로 표(§3, 양식 B) |
| 4 통지 | **72시간** | {발주처} 개인정보 보호책임자(운영사 PL 이 자료 준비) | 정보주체 통지문·감독기관 신고(해당 시) |
| 5 재발 방지 | 2주 | {운영사} PL + 개발 | 원인·조치·검증 결과, `SECURITY-POLICY.md §3` 갱신 |
| 6 기록·종결 | 종결 시 | {운영사} PL | 사고 기록 양식 완성본(§6), 보관 5년 |

**"사고 인지 시각"** = 신고를 받은 사람이 "유출 가능성 있음"으로 판단한 시각. 이 시각을 §6 양식에 먼저 적고 나머지를 진행한다(72시간 시계의 시작점).

## 1. 연락망

연락망은 문서에 이름·번호를 적지 않는다. **행사 설정에서 읽는다.**

| 역할 | 어디에 있나 | 하는 일 |
|---|---|---|
| {발주처} 개인정보 보호책임자(1명) | 운영사 설정 [기본 정보] → 개인정보 보호책임자(`programs.privacy_officer.client`) | 통지 문안 확정, 감독기관 신고 결정, 정보주체 통지 명의 |
| {운영사} PL(1명) | 같은 곳(`programs.privacy_officer.operator`) | 사고 지휘, 초동 조치, 영향 산정, 기록 |
| 플랫폼 관리자 | `/platform/users`(플랫폼 관리자 목록) · `OPS_ALERT_PHONES` | 계정 잠금·키 로테이션·Instant Rollback·백업 확인·Vercel/Supabase 대시보드 조작 |
| 발견자 | — | 최초 신고, 증거 보존, 이후 문의 응대 금지(PL 로 일원화) |

- 두 책임자는 §8-2 의 보안 알림 문자(warn 이상)를 **자동으로 받는다**. 문자를 받았는데 자기 담당이 아니어도 "받았음"을 서로 알린다.
- 행사에 `privacy_officer` 가 비어 있으면 플랫폼 관리자가 임시 책임자 역할을 하고, 사고 종결 전에 반드시 등록시킨다(§5 재발 방지 항목).
- 연락 순서: 발견자 → 운영사 PL → (동시에) 플랫폼 관리자 + 발주처 책임자. 15분 안에 연락이 안 되면 다음 순번이 대신 시작한다.

## 2. 신고 접수 → 초동 조치

### 2-1. 신고 접수(발견자·운영사 PL)
1. 무엇을 봤는지 **그대로** 적는다: 잘못 간 문자, 모르는 로그인 알림, 명단이 외부에 돌아다님, 화면에 남의 정보, `security_events` critical 문자 등.
2. **증거를 먼저 보존한다** — 화면 캡처(이 경우에만 캡처 허용), 문자 이력 화면, 받은 파일의 원본(열어보지 말고 보관), 이벤트 id.
3. 운영사 PL 에게 전화(문자·메신저만으로 끝내지 않는다). PL 이 §6 양식 A 를 열고 사고 번호(`INC-yyyymmdd-nn`)와 인지 시각을 적는다.
4. 발견자는 이후 외부(멘티·멘토·언론 포함) 문의에 답하지 않는다. 답변 창구는 PL 로 일원화.

### 2-2. 초동 조치 체크(운영사 PL + 플랫폼 관리자)
순서를 지킨다. 각 항목의 실행 시각과 실행자를 양식 A 에 적는다.

| # | 조치 | 언제 하나 | 어디서 |
|---|---|---|---|
| ① | **관련 계정 잠금** — 표적 계정, 의심 실행자(대행·반출), 유출된 계정 전부. 로그인 성공 흔적이 있으면 비밀번호 재설정 강제 | 항상 | `/platform/security` [잠금] · 회원 명단 [계정 잠금] |
| ② | **진행 중인 대행 종료·예약 문자 취소** | 대행·문자 관련 사고 | 회원 명단 대행 배너 [대행 종료] · 문자 발송 [예약] 탭 |
| ③ | **IP 차단·Attack Challenge Mode** | 외부 공격·폭주 | Vercel → `modu` → Firewall(`SECURITY-POLICY.md §8-3` 2단계) |
| ④ | **Instant Rollback** — 최근 배포가 원인(새 화면에서 남의 정보가 보임 등) | 배포 후 발생한 사고 | Vercel → Deployments → 직전 정상 배포 → Instant Rollback(`DEPLOY-RUNBOOK.md §7`) |
| ⑤ | **키 로테이션** — 침입 성공·키 유출 의심 | 서버 침입·키 노출 | 순서: `VIEW_AS_SECRET` → `CRON_SECRET` → Supabase 서비스롤·anon 키 → 재배포 → Supabase Auth "Sign out all users" → `SMS_KEK`(마지막, 구 KEK 90일 보관) → 행사별 문자 API 키 재등록(`SECURITY-POLICY.md §5-7·§8-3`) |
| ⑥ | **백업 보호** — 사고 이전 백업의 존재·크기·해시 확인, 30일 자동 삭제 대상에서 제외 표시 | 데이터 변조·삭제 의심 | `/platform/security` 백업 표 · `scripts/restore-backup.mjs --list`(`BACKUP-RESTORE.md`) |
| ⑦ | **행사별 문자 API 일시 해제** — 문자 API 를 통한 대량 오발송 의심 | 문자 관련 사고 | `/nextlab/settings/sms-api` [해제] |
| ⑧ | 잠금·차단으로 정상 업무가 멈춘 담당자에게 상황·예상 복구 시각 통보 | 항상 | 전화·문자(사고 내용은 말하지 않는다) |

- **판단이 서지 않으면 잠근다.** 잠금은 되돌릴 수 있고 유출은 되돌릴 수 없다.
- 복원(백업에서 되돌리기)은 초동 조치가 아니다. §3 영향 산정에서 "무엇이 언제 변조됐는가"가 나온 뒤에 결정한다(잘못 복원하면 정상 데이터까지 지운다).

## 3. 영향 범위 산정(24시간)

목표: **누구의 · 어떤 항목이 · 언제부터 언제까지 · 어떤 경로로** 노출됐는지 표로 만든다(§6 양식 B). 추정치는 "이상(≥)"으로 적고 근거를 남긴다.

### 3-1. 활용할 기록

| 기록 | 위치 | 무엇을 알 수 있나 |
|---|---|---|
| `security_events` | `/platform/security` | 유형(scan/bruteforce/impersonation/export/denied)·시각·IP·대상 계정·건수 — 공격의 시작·끝·범위 |
| `login_attempts` | `/platform/security` 로그인 시도 표 | 어떤 계정에 어떤 IP 가 언제 **성공**했는가(성공이 있으면 그 계정 권한으로 볼 수 있는 전부가 노출 범위 후보) |
| `audit_logs` | `/platform/audit`(전 행사) · `/nextlab/settings?tab=audit`(행사) · 엑셀 `/api/nextlab/audit-export` | 의심 계정·기간의 모든 변경 행위, 반출(`*.docs_zip_export`·`report.export`·`export.*`), 대행(`impersonation.start/stop`, `on_behalf_of`), 계정 발급·삭제, 설정 변경 |
| 문자·알림 이력 | 문자 발송 [이력] 탭, `notifications`, `program_sms_access_log` | 오발송 수신 번호·본문, 문자 API 자격증명 접근(`decrypt_fail`·`send_use`) |
| `error_reports` | `/platform/system` | 공격 시각대의 화면 오류(부수 효과) |
| `backup_runs` + 백업 파일 | `/platform/security` · `scripts/restore-backup.mjs --inspect <run>` | 사고 **이전** 데이터 상태와 비교 → 변조·삭제된 행 식별(복원 여부 판단 근거) |
| Vercel 로그·Firewall 이벤트 | Vercel → `modu` → Logs / Firewall → Traffic | 요청 경로·UA·국가(무료 플랜은 실시간만 — 발견 즉시 캡처) |
| Supabase Auth 로그 | Supabase → Authentication → Logs | 토큰 발급·재설정·OTP 발송 |

### 3-2. 산정 절차
1. **기간 확정**: `security_events` 최초 신호 시각(또는 오발송 시각) ~ 초동 조치 완료 시각. 확신이 없으면 앞뒤로 24시간 넓힌다.
2. **주체 확정**: 그 기간에 성공한 로그인·대행·반출을 한 계정과 IP. 정당한 담당자의 정상 작업은 본인 확인 후 제외(확인 기록 남김).
3. **범위 확정**: 주체의 역할·등급·행사 소속으로 "볼 수 있었던 최대 범위"를 정하고(예: 운영사 PM = 그 행사 멘티 전원 2급 + 정산 3급), 실제 접근 기록(반출 행 수·열람 화면)이 있으면 그 범위로 좁힌다. 기록이 없으면 **최대 범위로 본다**.
4. **항목 분류**: `SECURITY-POLICY.md §1` 등급으로 1급(신분증·통장·서명)/2급(연락처)/3급(아이디어·평가·정산) 구분. 1급 포함 여부가 통지 문안과 신고 판단을 좌우한다.
5. **인원 수 산출**: 케이스·회원 명단에서 범위에 든 정보주체 수(멘티·팀원·멘토·담당자 별도). 엑셀로 명단을 뽑되 이 명단 자체가 반출이므로 사고 폴더에만 보관.
6. **변조·삭제 확인**: 데이터가 바뀌었을 가능성이 있으면 사고 이전 백업과 비교(`BACKUP-RESTORE.md` 비교 절차). 복원이 필요하면 **복원 범위(테이블·행)를 정해 플랫폼 관리자가 수동 실행**하고 기록.
7. 결과를 양식 B 로 정리해 발주처 책임자에게 전달(24시간 내, 미완이면 중간본).

## 4. 통지(인지 후 72시간)

> 법정 기한·요건은 개정이 잦다. **{발주처} 개인정보 보호책임자가 현행 개인정보 보호법·시행령의 통지·신고 기준(대상 인원 수, 고유식별정보·민감정보 포함 여부, 해킹 등 외부 침입 여부)을 확인해 결정**한다. 이 문서는 "72시간 안에 결정과 통지를 끝낸다"는 내부 기준만 정한다.

| 대상 | 누가 | 방법 | 내용 |
|---|---|---|---|
| **정보주체**(영향 범위의 멘티·팀원·멘토·담당자) | {발주처} 책임자 명의, {운영사} PL 이 발송 | 플랫폼 문자(행사별 API 가 안전할 때) + 이메일. 연락처가 유출된 사고라면 **피싱 주의 문구** 포함 | ① 유출 항목 ② 시점·경위 ③ 피해 최소화를 위해 본인이 할 일(비밀번호 변경·의심 문자 주의) ④ 조치 내용 ⑤ 문의 창구(책임자 연락처) |
| **{발주처} 개인정보 보호책임자** | {운영사} PL | 전화 + 양식 A·B 전달 | 인지 즉시 1차, 24시간 영향 산정본, 72시간 내 통지 완료 보고 |
| **감독기관**(신고 요건 해당 시) | {발주처} 책임자 | 기관이 정한 창구 | 양식 B 기반. 신고 여부·시각·접수번호를 양식 C 에 기록 |
| **플랫폼 관리자·다른 행사 운영사** | 플랫폼 관리자 | 문자·전화 | 같은 배포를 쓰는 다른 행사에 영향이 있는가(키 유출·플랫폼 취약점이면 전 행사 통지) |

- 통지문에 **다른 정보주체의 정보를 넣지 않는다**(수신자 본인 항목만). 문자 `{name}` 치환은 수신자 본인만.
- 통지 발송 전 수신 번호를 다시 대조한다(오발송 = 2차 사고). 발송 결과(성공·실패 건수)를 양식 C 에 남긴다.
- 통지 문안은 발주처가 확정하되, 운영사 PL 이 초안을 12시간 안에 준비한다(문안 확정 대기로 72시간을 넘기지 않는다).

## 5. 재발 방지(2주)

1. **원인 분류**: 외부 침입(취약점·키 유출) / 내부자 오남용(대행·반출·권한) / 실수(오발송·잘못된 공유) / 설정(플래그·권한 override·허용목록) / 배포(회귀). 하나로 못 고르면 복수 기록.
2. **조치**: 원인별로 코드 수정(검증 4종 + 스모크 통과 후 main 반영), 권한·등급 축소, 규정(`SECURITY-POLICY.md §5`) 개정, 외부 보호장치(§8-6) 추가, 임계값·허용목록 조정.
3. **검증**: 같은 시나리오를 재현해 차단되는지 확인(스모크 시드 행사에서 재현 가능하면 그곳에서). 결과를 양식 D 에 기록.
4. **문서 갱신**: `SECURITY-POLICY.md §3` 진단표의 관련 행 상태·근거 갱신, 필요하면 §8-1 임계값 표와 `security-events.ts` 를 같은 커밋에서 수정.
5. **잠금 해제·정상화**: 초동 조치로 잠근 정상 계정 해제, 임시 Firewall 규칙 정리(사유 없는 30일 초과 규칙 제거), Attack Challenge Mode OFF, 키 로테이션 후 행사별 문자 API 재등록 확인.
6. **교육·공유**: 다음 분기 보안 교육(§6-2)에서 익명화한 사례로 공유. `privacy_officer` 미등록이 드러났으면 전 행사 등록 완료.

## 7. 모의 훈련

- 연 1회(§6-2 분기 점검 중 한 번) 가상 사고 1건("운영사 PM 계정에서 야간에 해외 IP 로그인 성공 + 명단 엑셀 반출")으로 §2~§6 을 실제로 수행하고 양식 A~D 를 채운다. 72시간 시계 대신 4시간으로 압축.
- 훈련에서 드러난 공백(연락 안 됨, 콘솔에서 못 찾음, 키 로테이션 절차 불명확)은 이 문서와 런북에 반영한다.
